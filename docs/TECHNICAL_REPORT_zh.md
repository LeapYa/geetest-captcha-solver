## 二、word / icon：形状匹配（本次最大突破）

### 2.1 走过的弯路

**第一版：模板匹配（连通域分割 + 全库模板检索）**

| 题型 | 结果 |
| --- | --- |
| word | 0~21% |
| icon | 35% |

失败原因：word 型的字**经常重叠成一团**，连通域会把 2~3 个字连成一块，
尺寸过滤（30~80px）时整块被丢弃，候选池只剩 1 个框。

**第二版：YOLO + OCR 识别 + 文字比对**

| 题型 | 结果 |
| --- | --- |
| word | 21% |

失败原因：OCR 在 word 上只有 **42%**（用人工框测的），
错误层层传递，最终结果更差。

**第三版（最终）：YOLO 检测 + 形状匹配**

| 题型 | 3 点全对 | 单点落框 |
| --- | --- | --- |
| **word** | **100%** | **100%** |
| **icon** | **99%** | **99%** |

### 2.2 关键洞察

**不需要识别文字。** word 和 icon 本质是同一个任务：
给定 ques 小图，在背景里找到它。

实测数据支持这个判断：

```
word: 203 个 ques 模板，同一字符永远对应同一个模板（1:1）
icon:  39 个模板，每个出现 2~13 次
```

**ques 模板是固定闭集**，所以这是检索问题，不是识别问题。

### 2.3 为什么形状能匹配上

ques 和背景里的字看起来差别巨大：

| | ques | 背景字 |
| --- | --- | --- |
| 外观 | 黑字 + 透明底 | 彩色描边 + 点阵纹理 |
| 尺寸 | 65×64 | 51~64px |
| 旋转 | 无 | ±30° |

但**归一化成二值形状后，结构信息保留着**。

### 2.4 算法

```python
def shape_of(img):
    """任意图 → 归一化的二值形状 64×64"""
    if img.shape[2] == 4:          # ques：用 alpha
        m = (img[:,:,3] > 20)
    else:                           # 背景：高饱和 + 高亮度
        hsv = cv2.cvtColor(img, cv2.COLOR_BGR2HSV)
        m = ((s > 100) & (v > 60)) | (v > 170)
        m = cv2.morphologyEx(m, cv2.MORPH_OPEN, ones(2,2))
    # 裁紧 + 等比缩放到 58px + 居中放到 64×64
    return canvas

def similarity(a, b):
    """多角度 IoU，取最大"""
    best = 0
    for ang in range(0, 360, 20):
        rb = rotate(b, ang)
        iou = (a & rb).sum() / (a | rb).sum()
        best = max(best, iou)
    return best

# 匈牙利算法分配，一框一目标
idx = match_boxes(bg, boxes, ques_shapes)
```

## 四、phrase：OCR + 语序

### 4.1 微调 PP-OCRv6

| 版本 | 单字识别 |
| --- | --- |
| PP-OCRv6 原版 | 58.8% |
| **微调后** | **95.4%** |

**三档模型对比（真实人工框，876 个字）**

| 档位 | 单字准确率 | 速度 | 动态图权重 | 字符表 |
| --- | --- | --- | --- | --- |
| **tiny** | **97.8%** | **21 ms/字** | 68.2 MB | 6,906 字 |
| small | 97.5% | 66 ms/字 | 119.1 MB | 18,708 字 |
| medium | 99.1% | 219 ms/字 | 221.9 MB | 18,708 字 |

**tiny 是意外之喜**：准确率比 small 还高（97.8% vs 97.5%），
速度是 medium 的 10 倍，权重只有 31%。

原因：tiny 用 6,906 字的**精简字符表**，候选空间小，误识更少。

> 注意：tiny 的输出层键名是 `head.ctc_head.fc2.bias`（两级），
> small/medium 是 `head.ctc_head.fc.bias`。字符表也不同，用错会全错（实测 0%）。

**静态图导出：68.2MB → 4.4MB**

动态图的 `.pdparams` 含优化器状态，导出成静态推理图后只剩推理所需权重：

```python
m = paddle.jit.to_static(model, input_spec=[...])
paddle.jit.save(m, "_onnx/ocr_tiny/model")
# model.json       0.14 MB
# model.pdiparams  4.28 MB
```

| 指标 | 动态图 | **静态图** | 变化 |
| --- | --- | --- | --- |
| 模型文件 | 68.2 MB | **4.4 MB** | **-94%** |
| OCR 内存增量 | ~150 MB | **14 MB** | **-91%** |
| 单字准确率 | 97.8% | 97.8% | 持平 |
| 速度 | 21 ms/字 | 26 ms/字 | 略慢 |

**为什么不再做 INT8 量化**

静态图已经 4.4MB，量化的边际收益很小。而且实测整体内存 900MB+ 的瓶颈在
**YOLO（torch）与 paddle 同时加载**，与 OCR 权重体积关系不大：

```
paddle 运行时本身:      ~270 MB
静态图 predictor 增量:     14 MB
YOLO26n (torch):        ~300 MB
```

继续压 OCR 权重对总内存影响不到 2%。

静态图已是最优解。

训练配置：

| 项 | 值 |
| --- | --- |
| 权重 | `PP-OCRv6_medium_rec_pretrained.pdparams`（221.9MB） |
| Backbone | PPLCNetV4 medium |
| 字符表 | `ppocrv6_dict.txt`（18708 字） |
| 数据 | 5436 训练 / 741 验证 |
| 学习率 | 0.0002，warmup 2 |
| 输入 | 3×48×320 |

**关键：预处理必须严格对齐**

| 预处理 | 单字识别 |
| --- | --- |
| **等比缩放到高 48 + 右补 0 到 320 + 归一化 [-1,1]** | **95.4%** |
| resize 到 64px 高、直接除以 255 | 46.7% |

同一份权重，差 49 个百分点。

### 4.2 语序模型

字符 3-gram + 词典命中奖励：

| 打分方式 | 准确率 |
| --- | --- |
| 纯 n-gram | 88.0% |
| **n-gram + 词典命中 +2.0** | **90.1%** |

### 4.3 端到端

```
292 张真实样本（融合后）：
端到端通过:  81.5%
失败:        18.5%
   其中语序错、识别错各占一部分
```

**瓶颈在语序，不在检测或识别。**

### 4.4 语序模型改进（2026-10-22，成功）

试了三种方案，最终 **n-gram + 分类器融合** 成功提升。

#### 4.4.1 三种方案对比

在 47 个「字符集完全未出现在训练集」的 phrase 词上（**零泄漏**）：

| 方案 | Top-1 | Top-3 | 说明 |
| --- | --- | --- | --- |
| 字符 3-gram | 85.1% | 95.7% | 基线 |
| 六选一分类器 | 80.9% | 97.9% | 单独用不如基线 |
| **融合（权重 0.4）** | **89.4%** | **100.0%** | **+4.3** |

在全部 252 个 phrase 词上：

| 方案 | Top-1 | Top-3 |
| --- | --- | --- |
| n-gram | 88.5% | 97.6% |
| 融合 0.4 | 93.3% | 98.8% |
| 融合 0.5 | 96.0% | 99.6% |

**端到端（292 张真实验证码）：77.1% → 81.5% → 90.8% → 90.1%（去 torch 后略降 0.7）。**

#### 4.4.2 关键：数据泄漏两次

第一次测出融合 **96.0%**，但发现 **85% 的测试词在分类器训练集里**。
在分类器从未见过的 38 个词上重测，融合只有 89.5%，**低于纯 n-gram 的 92.1%**。

修正方法：**按字符集划分**，同一组三个字的全部排列必须全在同一侧。

第二次修正后重训，训练集从 6,419 词扩到 **23,783 词**（用 LCCC 851 万行真实语料验证词的真实性），
分类器 Top-1 从 65.5% 提到 **73.1%**，融合终于超过 n-gram。

#### 4.4.3 为什么融合有效

两个模型互补：

| 模型 | 优势 | 来源 |
| --- | --- | --- |
| n-gram | 常见搭配 | 183MB 语料统计的 133 万条 3-gram |
| 分类器 | 整体构词合理性 | 2.4 万词的排列规律 |

单独用分类器（80.9%）不如 n-gram（85.1%），但**融合后 89.4%**。

#### 4.4.4 数据质量的关键作用

第一版数据集只有 6,419 词，用 jieba 词频≥100 过滤。
但 jieba 里「一万两」「一二九」这类数字组合混进来了。

改用**真实语料验证**：

```
jieba 三字词：131,321 个
在 LCCC 851 万行语料中出现过的：28,249 个（21.5%）
过滤「一」开头 + 纯数字后：28,765 个
```

词表从 6,419 → 28,765（**4.5 倍**），分类器 Top-1 从 65.5% → 73.1%。

**教训：词频不等于词的真实性，要在真实语料里验证。**

#### 4.4.5 失败的尝试

| 手段 | 结果 |
| --- | --- |
| 冻结 backbone（只训分类头） | 60.8%，更差 |
| 微调 IME 语言模型（4.25M） | 61.0%，不如 n-gram |
| 降低学习率 + 余弦退火 | 无改善 |

#### 4.4.6 轻量化（52.1MB → 16.7MB）

原始语序模块占 52.1MB，对 2H2G 服务器太重。压到 16.7MB（-68%），准确率不降反升。

**n-gram 提高计数阈值**

3-gram 表有 138 万项，大量只出现 1~2 次（噪声）：

| min_count | 项数 | 体积 | 纯 n-gram | 融合 |
| --- | --- | --- | --- | --- |
| 2（原版） | 1,380,694 | 35.6 MB | 87.2% | 89.4% |
| **5（采用）** | **404,701** | **10.8 MB** | **87.2%** | **91.5%** |
| 10 | 181,437 | 8.0 MB | 83.0% | 87.2% |

**min_count=5 最优**：体积减 53%，融合反而从 89.4% 升到 91.5%。
低频 3-gram 本是噪声，去掉后模型更稳。

**分类器 int8 量化**

二维权重按输出行对称量化，LayerNorm/bias 保 fp32：

```
真实值[行,列] = int8值[行,列] × scale[行]
scale[行] = max(abs(权重[行])) / 127
```

| 版本 | 体积 | 分类器 Top-1 | 融合 Top-1 | 融合 Top-3 |
| --- | --- | --- | --- | --- |
| fp32 | 16.5 MB | 80.9% | 89.4% | 100.0% |
| **int8** | **5.9 MB** | **83.0%** | **89.4%** | **100.0%** |

准确率零损失（分类器略升，量化有正则化效果）。

**为什么不换更小的模型**

试过换小架构，全部失败：

| 架构 | 参数 | Top-1 | 原因 |
| --- | --- | --- | --- |
| 6层192（保留） | 4.25M | 73.1% | 能加载官方预训练权重 |
| 4层128 | 1.85M | 55.6% | 维度不匹配，从零训练 |
| 2层128 | 1.45M | 60.4% | 同上 |

**官方预训练权重是关键。** 换架构就用不了它，从零训练在 2.4 万词上必然过拟合。
所以**保留架构 + 量化** 比换小架构效果好得多。

#### 4.4.7 最终方案

```python
分数 = 0.6 × n-gram归一化 + 0.4 × 分类器归一化
```

两个分数**量纲不同**，先各自 min-max 归一化到 [0,1] 再加权。

分类器权重 0.3~0.5 都能到 89.4%，取中间值 0.4。

### paddle2onnx 的 Windows 坑

在 Windows 上 `paddle2onnx` 的 wheel 缺依赖（`libpaddle.pyd`、`common.dll`），
装 2.1.0、2.0.2rc1、1.3.1 全部 `DLL load failed`。

- 1.3.1 能加载，但不认 Paddle 3.x 的 PIR 格式 `model.json`
- 2.x 加载不了，按 [CSDN 的解法](https://blog.csdn.net/FL1623863129/article/details/148338333)
  要把 paddle 也降到 `3.0.0.dev` nightly

**最终在 WSL 里导出**（Linux 下无此问题）：

```bash
# WSL Ubuntu
python3 -m pip install --user --break-system-packages paddlepaddle==3.3.1 paddle2onnx==2.1.0
python3 -c "import paddle2onnx; paddle2onnx.export(...)"
```

导出后在 Windows 上用 onnxruntime 推理，准确率 97.8% 与 paddle 完全一致，
速度从 26ms/字 提到 3ms/字。

### 三个隐蔽的性能 bug

**① `_ocr` 缓存没赋值**

```python
self._static = True
return self._pred        # ← 漏了 self._ocr = self._pred
```

每次调用重走完整加载流程，单字 137ms（正常 25ms）。

**② 两处检测调用，只改了一处**

`_detect_boxes` 和 `_segment` 各有一套检测逻辑，
换 ONNX 时只改了前者，后者还在调 torch 的 `det.predict()`，
异常被 `except` 静默吞掉，直接退回阈值分割，准确率掉到 0%。

**③ 静态图分支的字符表判断**

```python
self.ocr_dict = tiny_dict if "tiny" in self.ocr_weights.name else ...
```

静态图分支不走 `ocr_weights`，导致用错 18,708 字的字符表，
OCR 全部乱码（输出「挲佀早」而不是「马德里」）。

## 十二、2026-10 改版与重训（v4 里程碑）

### 12.1 改版事实

| | 旧数据（2026-05） | 现状（2026-10） |
| --- | --- | --- |
| phrase 字数 | 3 字 | **4 字** |
| 字形 | 彩色描边艺术字 | 白色粗描边 + 饱和填充 |
| 平均饱和度 | 161 | 112 |
| 白像素占比 | 6.8% | 16.4% |
| 接口 / 题型分布 | — | 未变（word 7/12、icon 2/12、phrase 3/12） |

旧模型在新字形上单字 52%、端到端 62.5% → 不可用。重新拉 400 张新样本
（`fetch_phrase4.py`）、人工核对 302 张、三轮微调。

### 12.2 OCR 三轮迭代结果

| 版本 | 训练数据 | 全量字块 | 留出字块 |
| --- | --- | --- | --- |
| v1 | 200 张 / 800 字 | 95.5% | 95.0% |
| v2 | 206 张 / 824 字 | 96.4% | 95.4% |
| **v3（线上）** | **302 张 / 1208 字** | **96.7%** | 95.0% |

留出集 240 字，差异在 ±1.4% 噪声内 → 单字能力已饱和。
端到端（留出 60 张 / 240 字）：**单字 95.0%、整句 85.0%、语序 80.8%、1.3 ms/字**。

### 12.3 训练成本优化（纯 CPU）

| 项 | 改前 | 改后 |
| --- | --- | --- |
| 输入尺寸 | 3×48×320 | **3×48×96** |
| batch | 8 | 32 |
| 吞吐 | 6.2 样本/秒 | 11.5 样本/秒 |
| 单 epoch | 24 min | 15 min |
| 20 epoch | 8.3 h | 3 h（12 epoch） |

- 字块缩到高 48 后宽度只有 ~44px，320 宽 90% 是 padding
- **窄宽训练必须窄宽推理**：96 宽训的模型按 320 跑，96.1% → 88.9%
- 砍 NRTR 头（只留 CTC）理论再快 1.4 倍，但 PaddleOCR `MultiHead` 硬编码，
  改配置仍实例化 NRTR 并崩在 `targets[1]`，放弃

### 12.4 4 字语序方案

| 方案 | Top-1（245 条去重真实题面） |
| --- | --- |
| 字符 n-gram | 34.3% |
| 六选一分类器（3 字任务训的） | 5.5% |
| 旧融合 0.4 | 27.6% |
| 24 选一 ranker（LCCC 挖掘训练） | 48.3%（挖掘集 85.6%，分布不匹配） |
| 位置字频模型（量词锚点 84 万窗口） | 46.9% |
| **谓宾结构先验（`order_pos.py`）** | **80.8%** |

句式：`动词 + (量词) + 宾语`，另补 `状语+动+宾`、`动+补+宾`。
剩余错误：标注歧义（好排队伍/排好队伍）+ 双字名词内部顺序（花茶/茶花），
需短语级语料统计，规则到顶。

### 12.5 标注数据质量（三个坑，务必先查）

1. **「上一张自动保存」串行**：`label[i]` 存成了 `image[i+1]` 的框和字，
   影响 9 条 + 11 条整组框错位；
2. **不能用训练过的模型做数据审计**：OCR 会"照着标签读"，
   一片天空也能输出「顶」（置信度 0.99）→ 改用白像素占比
   （字块 0.18~0.25，背景 <0.06）检出 11 条；
3. **误拖产生的空格垃圾框**（17×54）会混进训练集 → 生成时按 `w<30 or h<30` 过滤。

工具：`audit_live4_align2.py`（图像信号审计）、`fix_box_shift.py`（重新预填）、
`audit_live4_order.py`（语序审计）、`merge_review.py`（复核结果合并）。

### 12.6 关于「惩罚训练」的结论

可以写（`loss = CE + λ·relu(s_违规 − s_正确 + margin)`，或解码时 mask 违规候选），
但当前没有可罚对象：245 条真实题面 49 条排序失败中，**0 条**是模型选了违反谓宾结构的
顺序（线上是硬约束排序）。剩余错误是"规则与标注分歧"，需短语级统计或更多标注，
不是损失函数能解决的。

## 十三、关键教训

1. **先想清楚任务本质** —— word/icon 是「检索」不是「识别」，我绕了远路
2. **权重地址要看文档** —— `official_pretrained_model` vs `official_inference_model`
3. **预处理必须与训练严格一致** —— 48px vs 64px 差 49 个百分点
4. **业务指标优先于 mAP** —— v26n 的 mAP50-95 略低但字数正确率高 8%
5. **重叠目标是连通域的死穴** —— 必须用检测模型
6. **数据审计要独立于被审计的模型** —— 用训练过的 OCR 查标签错位会全票通过
7. **协议没变、分布变了** —— 先比对接层，再怀疑模型
8. **窄宽训练必须窄宽推理** —— 尺寸不一致掉 7 个点
9. **结构先验 > 打分融合** —— 三类融合都不如把句式写死
